Primer 0

0. From regression to XGBoost

Every supervised model is three choices: a score function (what shape of answer it can produce), a loss (how wrong an answer is), and a way to minimize the loss. Each model below exists because the one before it hit a wall.

Prefer to watch? Score, Loss, Wall animates this whole section in about 4½ minutes.

Logisticstraight line in log-odds + log loss

Two ways a model can be wrong

Bias: the model is too simple to capture the pattern, so it's wrong in the same way every time (a straight line through a curve). Variance: the model is so flexible it memorizes noise, so retraining on slightly different data gives a very different model. The history below is a back-and-forth between these two.

1805
Least squares
Starting point

Linear regression

How
Predict a number as a weighted sum: ŷ = w₁x₁ + w₂x₂ + … + b. Pick the weights that minimize the average squared error (y − ŷ)². There's a closed-form solution, so no iteration needed.
Where
Forecasting continuous values (price, demand), and measuring effects: "each extra bedroom adds $X". Still the default in economics and science.
Explain
Fully: each weight is "change in prediction per unit of this feature".
Wall
For classes, it predicts unbounded numbers (−0.3, 1.4) that aren't probabilities, and straight lines miss curves and interactions.
1958
Cox
Fixes: outputs

Logistic regression

How
Keep the weighted sum, but treat it as log-odds: z = w·x + b, then squash it into a probability with the sigmoid p = 1 / (1 + e−z). Train by minimizing log loss −[y·log p + (1−y)·log(1−p)] with gradient descent. For 3 classes, use one score per class and softmax (multinomial logistic regression).
Where
Credit scoring, clinical risk scores, any regulated setting where every coefficient must be defensible. The standard baseline for classification.
Explain
A weight is "change in log-odds per unit of feature"; ew is the odds ratio. The intercept b is the log prior odds when features are zero (Primer B).
Imbalance
Same prior problem as everything else. class_weight="balanced" in scikit-learn shifts the intercept by roughly log w.
Wall
Log-odds must be a straight-line function of features. Thresholds ("risk jumps above age 60") and interactions ("only if both A and B") must be hand-built as features.
1984
CART, Breiman et al.
Fixes: bias

Decision tree

How
Repeatedly pick the single feature and cutoff that best separates the rows (lowest Gini impurity or entropy for classes, lowest squared error for numbers). Each leaf predicts its rows' majority class or average. The result is a step function.
Where
Rule-based decisions people need to read: eligibility, triage, policy rules.
Why needed
Finds thresholds and interactions automatically, handles mixed feature types, needs no scaling.
Wall
High variance. A deep tree memorizes training data, and changing a few rows can produce a completely different tree.
2001
Breiman
Fixes: variance

Random forest

How
Grow hundreds of deep trees, each on a bootstrap sample (rows drawn with replacement), and at each split consider only a random subset of features. Average their predicted probabilities. The trees are independent, so their individual memorized noise averages out (this is "bagging").
Where
Strong, low-tuning default for tabular data; remote sensing, bioinformatics, quick baselines.
Why needed
Keeps the tree's flexibility while cutting its variance.
Imbalance
A bootstrap of 10,000 rows may hold only ~100 rare rows, so each tree sees little of them. class_weight="balanced_subsample" or imbalanced-learn's BalancedRandomForestClassifier (each tree gets a balanced sample) are the usual fixes.
Wall
Averaging reduces variance, not bias. Every tree is built independently, so no tree learns from the others' mistakes, and subtle patterns that need many small corrections get missed.
2001 → 2016
Friedman; Chen & Guestrin
Fixes: bias, sequentially

Gradient boosting, then XGBoost

How
Instead of independent deep trees, add shallow trees one after another, each fit to the current model's errors, and sum them. The faint line in the sketch is the first tree; the bold one is after several corrections.
The link
For squared error the gradient is ŷ − y, the residual from linear regression. For log loss it's p − y, the same form as logistic regression. So boosting is logistic regression where the straight-line score is replaced by a sum of trees. The score is still log-odds.
XGBoost added
Second-order information (the hessian), explicit regularization (lambda, gamma), built-in missing-value handling, and fast parallel split finding. LightGBM (2017) and CatBoost (2018) are later variants of the same idea.
Where
The go-to for structured/tabular data in industry and most tabular Kaggle wins.
Explain
Not by reading weights, but SHAP values give exact per-row, per-feature contributions to the log-odds score, the same units as a logistic coefficient.

The thread to keep

  • Logistic regression and XGBoost both output a log-odds score and both minimize log loss. Everything about priors in Primer B applies to both.
  • Random forest averages votes instead, so its "probabilities" are vote shares, usually less well calibrated, but the prior problem is the same.
  • For your data: logistic regression is a useful explainable baseline; if XGBoost doesn't beat it on macro-F1, the features, not the model, are the bottleneck.
Primer A

A. How XGBoost trains

Zooming into the last step of the lineage: what actually happens inside each boosting round.

A tree outputs a number, not a class

A single regression tree asks yes/no questions about features (age < 40?, balance > 2,000?) until it reaches a leaf. Each leaf holds a score, like +0.8 or -0.3. On its own, one tree is a crude step function.

Boosting adds trees one at a time

XGBoost starts with a constant guess and then adds trees, each one built to fix what the current model still gets wrong. The final score for a row is a sum:

F(x) = base + η·tree1(x) + η·tree2(x) + … + η·treeM(x)

η is the learning rate (e.g. 0.1). It shrinks each tree's contribution so no single tree dominates.

Scores become probabilities with softmax

With 3 classes, XGBoost keeps three scores per row, one per class, and each boosting round grows one tree per class. Softmax turns the scores into probabilities that sum to 1:

pk = eFk / (eFA + eFB + eFC)

"What's wrong" is the gradient

For every row and every class, XGBoost computes two numbers from the log loss:

g = p − y   (gradient: which way to push, and how hard)
h = 2·p·(1 − p)   (hessian: how confident / curved; XGBoost's multiclass form)

y is 1 if the row really is that class, else 0. Example, looking only at class C's score track, where the model currently says pC = 0.01 everywhere:

Row's true classpCyCgCMeaning
C0.011−0.99"Raise my C score a lot"
A0.010+0.01"Lower my C score a tiny bit"

How a tree picks splits and leaf values

A leaf's value comes from the sums of g and h of the rows that land in it (call them G and H; λ is L2 regularization, default 1):

leaf value = −G / (H + λ)

A split is kept if it increases this gain by more than γ (the gamma parameter):

gain = ½ · [ GL²/(HL+λ) + GR²/(HR+λ) − (GL+GR)²/(HL+HR+λ) ] − γ

In plain terms: a split is good when it separates rows that want to be pushed up from rows that want to be pushed down. If the rows in a region pull in opposite directions and cancel out, G ≈ 0 and the tree sees nothing to fix there.

Where imbalance bites, in this machinery

  • Cancellation. Take a region with 10 C rows and 990 A rows. On C's track: G = 10·(−0.99) + 990·(+0.01) = −9.9 + 9.9 = 0. The many small majority gradients exactly cancel the few big rare ones, so no tree splits there. This isn't a bug: in that region C really is 1%, so pC = 0.01 is the correct answer. Primer B explains why.
  • min_child_weight blocks small rare leaves. A leaf needs H ≥ min_child_weight (default 1). Ten C rows at p = 0.01 have H = 10 · 2 · 0.01 · 0.99 ≈ 0.2, so a leaf holding just those rows is not allowed. You'd need about 50 of them. A non-obvious knob worth lowering for rare classes.
  • sample_weight is just a multiplier on g and h. Weight 5 on a row means its g and h count 5×. That's the whole mechanism: it breaks the cancellation above and gets past min_child_weight.
Primer B

B. Priors, likelihoods and posteriors

Three quantities

NameNotationQuestion it answersIn your data
PriorP(C)Before looking at this row, how common is C?1% (100 of 10,000)
LikelihoodP(x | C)If a row is C, how typical are these features?Learned from the 100 C rows
PosteriorP(C | x)Given these features, how likely is this row C?What you want the model to output

The likelihood and posterior read alike but are different things. "Most C rows have this pattern" is not the same as "most rows with this pattern are C".

Count it out

10,000 rows. 100 are C, 9,900 are not. A feature pattern shows up in 50% of C rows and in 5% of the others. So this pattern is 10× more typical of C.

C rows: 100
Others: 9,900
Rows with pattern: 545

Of the 545 rows with the pattern, only 50 are C: 50 / 545 ≈ 9%. Bayes' rule is just this counting written as a formula:

P(C | x) = P(x | C)·P(C) / P(x) = (0.50 × 0.01) / (0.50 × 0.01 + 0.05 × 0.99) ≈ 0.09

The odds form, which is what XGBoost uses

Odds are p / (1 − p). Bayes' rule becomes a multiplication:

posterior odds = prior odds × likelihood ratio   →   (1/99) × 10 = 10/99  →  p = 10/109 ≈ 9%

Take logs and it becomes addition:

log posterior odds = log prior odds + log likelihood ratio

Look back at Primer A: XGBoost's raw scores are log-odds (the gap between two classes' scores is their log-odds). The starting score plays the role of the log prior odds, and each tree adds a bit of log evidence from the features. Boosting is Bayes' rule in log space, learned piece by piece.

Why this hides the rare classes

A model trained with log loss is trying to output the true posterior. The prior it bakes in is the class mix in your training data. For argmax to pick C over A, the posterior for C has to be the largest, which with a 1% prior needs features about 99× more typical of C than of A. Most real C rows don't have evidence that strong, so they get labeled A, even though the model's 9% may be perfectly accurate.

How this connects to the rest of the page

  • Class weight w multiplies C's gradients (Primer A), so the model behaves as if C's prior odds were w× larger. That adds log w to C's score.
  • Threshold multiplier w on pC also adds log w to C's score, but after training. Same move, no retraining. That's section 3.
  • Better features raise the likelihood ratio, the only term that actually makes the model more sure. That's the separation slider in the lab.
  • Calibration checks that the posterior the model outputs matches real frequencies. Weighting breaks that, because the model is now using a fake prior.
First principles

1. Why the rare classes lose

Take a dataset of 10,000 rows split like this:

A · 96%
A 9,600 rows · B 300 rows · C 100 rows

Reason 1: the loss is an average over rows

XGBoost minimizes log loss averaged over every training row. Every row gets one equal vote. A model that has learned nothing and just outputs the class proportions (0.96, 0.03, 0.01) for every row already scores:

accuracy = 96%    log loss = -(0.96·ln 0.96 + 0.03·ln 0.03 + 0.01·ln 0.01) ≈ 0.19

Getting B and C right moves that average only a little, because they are 4% of the votes. Each tree split is chosen by how much it reduces total loss, so splits that carve out the majority win the early rounds. The rare classes get attention only once the majority has nothing left to give.

Reason 2: Bayes' rule pulls rare probabilities down

Even a perfect model outputs the true posterior probability, and that includes the prior:

P(C | x) = P(x | C)·P(C) / Σk P(x | k)·P(k)

Say a row's features are 10× more typical of C than of A. With a 1% prior:

P(C | x) = (10 × 0.01) / (10 × 0.01 + 1 × 0.99) ≈ 0.09

The evidence strongly favors C, and the honest answer is still "9% C". Predicting with argmax picks A. So the model is often not wrong. Its probabilities can be fine; it's the decision rule (argmax, which implicitly means "pick C only above ~50%") that hides the rare classes.

Reason 3: rare classes have few examples to learn from

100 rows of C means the model sees only a thin sample of what C looks like, and a handful of mislabeled C rows is a big share of that sample. This is the one problem no training trick fixes; only more or better data and features do.

So there are two separate problems. Separability: how much the classes overlap in feature space (fixed by data and features). The decision rule: where you draw the line inside that overlap (fixed by weights, thresholds, resampling). The lab below lets you feel the difference.

The one big idea

3. Weights, resampling and thresholds are the same knob

Give the rare class weight w during training. In the limit of enough data, the model learns a distorted posterior where the rare class's prior is multiplied by w:

Pw(rare | x) ∝ w · P(x | rare) · P(rare)

Taking argmax of that is exactly the same as training normally and taking argmax(p · [1, w]). Oversampling the rare class w times does the same thing too, since it's the same as giving each copy weight 1. So:

TechniqueWhat it changesCost
Class weightsMoves the boundary at training timeRetrain to change it; probabilities are distorted
Oversampling / SMOTEMoves the boundary at training timeRetrain, bigger data, leakage risk in CV
UndersamplingMoves the boundary, throws away majority dataLoses information
Threshold multipliersMoves the boundary after trainingSeconds, probabilities stay honest
Better features / clean labelsPulls the curves apartThinking time

With finite data, weighting isn't quite identical to thresholding: it also makes the tree builder pay more attention to rare rows when choosing splits, which can help a bit. That's why mild weights plus a tuned threshold is a common combination. But the big wins come from the last row.

The toolbox

4. The methods

Each one: how it works, where people use it, how to do it in XGBoost, and whether the evidence says it's worth it for boosted trees.

Data side
Biggest lever

Better features and clean labels

How
Look at the confusion matrix and pull out rows where B is predicted as A, or C as B. Ask a domain expert what distinguishes them that your features don't capture. Separately, find likely mislabeled rare rows (a rare row the model is very confident is majority is often a labeling error).
Where
Every winning write-up. The PLAsTiCC Kaggle winner (14 heavily imbalanced classes) won on feature engineering and training-set augmentation, not resampling.
Why
It's the only thing that raises the ceiling. In the lab, this is the separation slider.
# flag likely label errors using out-of-fold probabilities
from cleanlab.filter import find_label_issues
issues = find_label_issues(labels=y, pred_probs=oof_proba,
                           return_indices_ranked_by="self_confidence")
Post-training
Highest ROI trick

Per-class threshold multipliers

How
Get out-of-fold probabilities (each row predicted by a model that never saw it). Search for multipliers [1, w_B, w_C] that maximize macro-F1 of argmax(proba · w). Apply the same multipliers at inference.
Where
Standard in competitions and production. A 30-dataset study found threshold tuning the most consistently effective option against SMOTE and weights (binary tasks).
Watch
Never tune on the same rows you trained on. With very few rare rows, the chosen multiplier is noisy; use repeated CV and prefer a round value in a flat region of the F1 curve.
oof = cross_val_predict(model, X, y, cv=StratifiedKFold(5, shuffle=True),
                        method="predict_proba")
best = max(((wb, wc) for wb in np.geomspace(1, 50, 30)
                     for wc in np.geomspace(1, 50, 30)),
           key=lambda w: f1_score(y, np.argmax(oof * [1, *w], 1), average="macro"))
Training time
Use mildly

Class / sample weights

How
Each row's loss and gradient get multiplied by its weight, so a rare row counts as w rows. "Balanced" weight = total / (n_classes × class_count). "Square root balanced" takes the square root of that, a gentler push.
Where
XGBoost: pass sample_weight to fit (scale_pos_weight only works for binary). LightGBM: class_weight. CatBoost: auto_class_weights="SqrtBalanced".
Also
Lower min_child_weight (e.g. 0.1 to 0.5) so leaves can form around small groups of rare rows (see Primer A).
Watch
Probabilities come out inflated for rare classes. Clinical prediction studies found weighting hurt calibration without improving ranking (AUC). If you need real probabilities, recalibrate.
from sklearn.utils.class_weight import compute_sample_weight
w = compute_sample_weight("balanced", y_train) ** 0.5   # sqrt-balanced
model.fit(X_train, y_train, sample_weight=w)
Post-training
If you need probabilities

Probability calibration

How
Fit a small mapping from the model's scores to observed frequencies on held-out data. Sigmoid (Platt) fits 2 parameters; isotonic fits a step function and needs more data.
Where
Anywhere the probability itself is used: risk scores, expected cost, ranking for review queues. Not needed if you only output a class label.
Watch
With ~100 rare rows, isotonic overfits. Use sigmoid.
from sklearn.calibration import CalibratedClassifierCV
cal = CalibratedClassifierCV(model, method="sigmoid", cv=5).fit(X, y)
Training time
Try later

Problem decomposition

How
Two-stage: model 1 predicts A vs "not A"; model 2, trained only on B and C rows, picks B vs C. One-vs-rest: three binary models, one per class, each with its own threshold.
Where
Fraud and medical triage pipelines (screen, then classify). Useful when B and C are confused with each other more than with A, since model 2 can focus on what separates them.
Bonus
Cleaner explainability: SHAP values per binary model answer "why rare?" and "why B not C?" separately.
Watch
No strong head-to-head evidence that it beats one softmax model. Compare on out-of-fold macro-F1.
Training time
Try later

Focal loss

How
Replaces log loss with -(1-p)γ · log p, where p is the probability of the true class. Rows the model already gets right (p near 1) contribute almost nothing, so training focuses on hard rows, which are disproportionately rare-class rows.
Where
Came from object detection (RetinaNet). For boosted trees it needs a custom objective with hand-written gradient and hessian; a 2024 study and package exist.
Watch
Moderate evidence, extra tuning (γ), and it also distorts probabilities. After weights and thresholds, not before.
Training time
Mostly skip

Resampling: SMOTE, oversampling, undersampling

How
Random oversampling duplicates rare rows. SMOTE creates synthetic rare rows by picking a rare row, one of its nearest rare neighbors, and interpolating a point on the line between them. Undersampling drops majority rows.
Where
Popular in tutorials and with weak learners (logistic regression, single trees, SVMs).
Why skip
A 73-dataset study (Elor & Averbuch-Elor, 2022) found balancing doesn't help strong learners like XGBoost, LightGBM, CatBoost; threshold tuning matched it, and plain duplication matched SMOTE. From section 3, it's just a slower way to move the boundary. SMOTE can also invent points in regions that belong to the majority, and its interpolation is meaningless for categorical features.
If you do
Resample inside each CV training fold only, never the validation fold, using imblearn.pipeline.Pipeline. Resampling before splitting leaks copies of validation rows into training.

5. Measuring it honestly

MetricUse it?Why
AccuracyNo96% for a model that never predicts B or C.
Macro ROC-AUCCarefulCounts true negatives, which are plentiful, so it looks good even when rare precision is terrible.
Per-class precision, recall, F1YesShows exactly which class fails and how.
Macro-F1Yes, as the headlineAverages F1 across classes equally, so B and C count as much as A.
Per-class PR-AUC (average precision)YesThreshold-free view of how well the model ranks each rare class.
Confusion matrixAlwaysTells you whether B is lost to A or to C, which drives the fix.

Stratified K-fold keeps each class's share the same in every fold; without it, a fold can end up with 5 C rows or zero. With under ~100 rows in a rare class, repeat the CV with different seeds and look at the spread, since one fold's F1 is noisy. Everything you tune (thresholds, calibration, resampling) is fit inside the folds.

Recommended order

6. What to do, in order

  1. Baseline. Unweighted XGBoost, stratified 5-fold, save out-of-fold probabilities. Record per-class PR-AUC, macro-F1 and the confusion matrix.
  2. Thresholds. Tune per-class multipliers on those OOF probabilities. This alone often closes much of the gap for free.
  3. Look at the errors. Inspect misclassified rare rows. Check for label errors. Engineer features that separate the confused pairs. Re-run 1 and 2.
  4. Mild weights. Square-root balanced sample_weight, re-tune thresholds, keep it only if OOF macro-F1 improves.
  5. Calibrate (sigmoid) if anyone consumes the probabilities.
  6. Optional: two-stage or one-vs-rest models, focal loss. SMOTE only if it beats everything above on OOF macro-F1.
